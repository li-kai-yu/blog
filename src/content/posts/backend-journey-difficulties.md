现在回头看，我的后端学习像一条被拉长的折线：每学完一个阶段，都以为接下来会顺，结果下一个问题又把人按回原地。

这篇不列知识点，只写那些真正卡住我的地方。

## Java 基础：听懂和写出来是两件事

面向对象的三大特性，我第一天就能背。封装、继承、多态，说起来头头是道。

但老师让我写一个「图书借阅」的小程序时，我写出来的还是一堆 `main` 方法里的 `if`。类只是把变量装在一起，没有任何行为上的边界。

后来我强迫自己写了一个命令行记账工具：收入、支出、分类、统计，全部拆成对象。写到一半才理解封装不是为了好看，而是为了改一个地方时不牵连其它地方。接口也不是形式，它让调用方只依赖能力，不依赖实现。

真正学会一个概念，不是能解释它，而是能在代码里用它做决定。

## 集合与并发：背完八股还是不会用

HashMap 的扩容、链表转红黑树，我能讲得很细。可项目里要选一个集合时，我还是下意识写 `ArrayList`。

线程池更典型。核心参数背得滚瓜烂熟，第一次在项目里用，却把任务队列设成了无界。压测时内存一路涨，我还以为是数据库慢。后来才明白，队列无界意味着任务永远排得进去，拒绝策略形同虚设，问题只是被推迟到了内存溢出。

那段时间我开始逼自己把每个八股题翻译成一个场景：这个参数调大，系统会先在哪里出问题。答不上来，就说明只是背过，没有理解。

## Web：从 Servlet 到 Spring Boot 的环境地狱

第一次搭 Spring Boot 项目，光环境就折腾了两天。

Maven 依赖冲突、JDK 版本不匹配、端口被占用、配置文件没被加载，每一个问题都不难，但凑在一起就足够让人怀疑自己。

印象最深的是依赖冲突：明明只引入了一个 starter，启动却报类找不到。翻了很多资料才知道，传递依赖带进来了另一个版本。那一刻我第一次意识到，构建工具也是需要理解的，不能只会复制 `pom.xml`。

当第一个接口终于返回 JSON 时，我盯着浏览器看了很久。那点成就感，足够支撑我继续往下学。

## 项目：没有教程之后的空白

跟教程写项目时，问题都有标准答案。MukoBazaar 不一样，它是我自己起的名字，第一次没有现成需求文档。

商品怎么建模、订单和库存怎么拆、搜索走数据库还是搜索引擎，每个决定都没有参考答案。最难的是下单：既不能超卖，也不能出现订单写成功而库存没扣。我改了三版方案，才把「先扣库存还是先建订单」想清楚。

那种压力很难受，但也第一次让我觉得，自己是在做工程，而不是在抄作业。

## 分布式：拆开之后才知道难

单体应用写得再乱，至少问题都在一个进程里。拆成微服务之后，问题开始变得看不见。

一次消息重复消费，让我排查了整整一个晚上：消费者重启后重复处理同一条消息，库存被多扣。后来加了唯一键和消费记录，才把幂等补上。

还有 Elasticsearch 和数据库不同步。它不报错，只是让用户搜到旧数据，反而更难发现。最后靠定时补偿和 binlog 订阅才稳定下来。

分布式没有银弹。每一个「方便」，背后都有一份需要自己承担的复杂度。

## 写给自己

这些坎没有一个是靠看一篇文章跨过去的。它们都是靠反复改代码、查日志、推翻自己，才慢慢想明白。

困难不会消失，只是会换一种形式出现。现在遇到问题时，我至少不再急着找「正确答案」，而是先问清楚：它卡在哪一层。
