我很少回头看自己学过的课程。它们像一串被默认接受的顺序，学完一个就进入下一个，很少有人问为什么是这个顺序。

直到有朋友问我「后端该从哪里开始」，我发现自己竟然很难用几句话回答。于是我把这一年多走过的路整理了一遍，按阶段写下当时的困惑，以及后来才意识到的不足。它不是标准答案，只是一个普通学习者的样本。

## Java SE 上：从语法到面向对象

上册是打地基。变量、流程控制、数组、方法、类和对象，内容并不难，难的是把「写代码」这件事变成习惯。

当时我最大的困惑是：为什么老师反复强调封装，明明把字段设成 public 也能跑。后来写项目时才明白，封装不是为了运行时不出错，而是为了让改动只发生在一个地方。

暴露的不足是练习太少。很多语法我「看懂了」，但一合上视频就写不出来。

## Java SE 下：第一次感到吃力

下册开始涉及集合、IO、多线程、网络编程、反射和注解，难度明显上了一个台阶。

我在这里第一次体会到「懂了」和「会用」之间的距离。比如线程安全，概念听懂了，可真正让我记住的，是一次共享变量被两个线程改乱的调试过程。

这部分我学得不算扎实，直到后面做项目才一点点补回来。

## MySQL：从会写到会想

学 MySQL 之前，我以为 SQL 就是增删改查。真正开始写多表查询、理解索引和事务之后，才发现数据库更考验的是判断：这条 SQL 为什么会慢，这个索引为什么没生效。

这一阶段暴露的不足是对执行计划太陌生。我习惯先写出来再说，很少主动去看 EXPLAIN。

## Java Web：把请求链路走通

Java Web 是我认知变化最大的一段。Servlet、Filter、JDBC、MyBatis、Maven 学完，我第一次能把「浏览器输入地址」到「数据库返回数据」完整串起来。

困惑也随之而来：既然有 Spring Boot，为什么还要学 Servlet。后来我理解了，框架只是把这条链路封装得更顺手，底层的容器和请求模型并没有消失。

## Redis：学会为性能做取舍

Redis 让我第一次认真思考「什么时候该用缓存」。它不是万能加速器，而是一种用一致性换性能的选择。

这一阶段我的问题是把缓存当成结论来记。穿透、击穿、雪崩背得很熟，但真正设计时，还是容易忽略过期时间和空值兜底这些细节。

## MukoBazaar：把自己的想法做成项目

MukoBazaar 是我第一个带个人判断的项目。集市、商品、交易这些设定，需要我自己决定表结构、接口和模块边界。

它暴露的问题最真实：没有现成需求文档，我必须自己想清楚哪些功能先做、哪些先放着。这种取舍，是课程里学不到的。

## Spring Cloud、RabbitMQ 与 Elasticsearch

到了分布式阶段，我学的不再是单个技术，而是它们如何配合。注册配置、远程调用、网关、限流、消息、搜索，每一项都对应系统变大后的某种痛。

这一段我最大的感受是：技术变多了，判断反而更重要。不是所有系统都需要微服务，也不是所有异步都值得引入消息队列。

## 对计算机专业的一点看法

我越来越觉得，这个专业最大的风险不是课程太难，而是把「上课」当成了学习的全部。

学校的课程给出的是骨架：数据结构、操作系统、计算机网络、数据库。这些值得认真学，但它们离做出一个真正能跑的系统还有很长的距离。老师能保证进度，却没法替你决定要做什么、要补什么。

所以真正的分水岭是有没有自学能力。我的做法很朴素：每学完一块内容，就找一个能用到它的小项目；遇到不会的，先查官方文档和源码，再去看别人的方案。慢一点没关系，关键是自己能往前走。

另一个感受是，不要只盯着语言和框架。技术会更替，判断力不会。知道一个方案为什么合适、代价是什么，比记住怎么调用 API 重要得多。

如果让我给同专业的同学一句话：把课程当作底线，把自学当作主线。

## 给后来者的三条建议

第一，不要跳过基础。Servlet、JDBC 这些看起来「过时」的内容，决定了你理解框架时的深度。

第二，项目要有自己的改动。照抄教程只能证明你会跟着做，能改需求、加功能，才算真正拥有它。

第三，每个阶段结束都写一次复盘。不用长，写清楚学了什么、哪里没懂、下一步补什么，就已经足够。

回头看，这条路线并不完美，中间有反复，也有很长一段停滞。但它至少是连续的。对学习者来说，连续比完美更重要。
