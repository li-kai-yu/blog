学网络时我最大的困惑是：HTTP 和 TCP 到底谁管什么。很多资料把它们混在一起讲，背完之后还是不知道一个请求是怎么发出去的。

后来我强迫自己按层次拆开，才把这条链路理顺。

## 先分清两层

HTTP 是应用层协议，它规定请求和响应长什么样：方法、路径、头部、状态码、正文。

TCP 是传输层协议，它不关心里面装的是网页还是 JSON，只负责把一段字节可靠地送到对面。

用寄快递打比方：HTTP 是包裹里的清单和物品，TCP 是物流系统。清单写得再清楚，物流丢了件，收件人也拿不到。

## TCP：先建立一条可靠的连接

发送数据之前，双方要握手三次：客户端发送 SYN，服务端回复 SYN + ACK，客户端再回 ACK。

为什么不能两次？因为两次只能确认「客户端能发、服务端能收」，服务端无法确认客户端也具备接收能力。三次之后，双方都确认了彼此的收发能力。

断开连接要四次挥手，因为 TCP 是全双工的，两个方向需要分别关闭。主动关闭的一方会进入 `TIME_WAIT`，等待两个最大报文段寿命，确保最后的 ACK 能被对方收到，也避免旧连接的报文干扰新连接。

这些细节平时写业务代码用不到，但排查「端口耗尽」「连接无法复用」时，它们就是答案。

## 一次 HTTP 请求的形状

一个请求由请求行、请求头和请求体组成：

```bash
POST /api/orders HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer <token>

{"skuId": 42, "count": 1}
```

响应则是状态行、响应头和响应体。HTTP/1.1 默认开启长连接，同一个 TCP 连接可以复用多次请求，减少握手开销。

HTTP/2 在一条连接上做多路复用，把请求拆成帧交错发送，解决了 HTTP/1.1 的队头阻塞；HTTP/3 干脆换到基于 UDP 的 QUIC，把可靠传输做进了用户态。

## 状态码与缓存

状态码不需要背全，但要按段理解：2xx 成功，3xx 重定向，4xx 客户端问题，5xx 服务端问题。

后端开发最常打交道的几个：`301` 永久重定向、`302` 临时重定向、`304` 命中协商缓存、`400` 参数错误、`401` 未认证、`403` 无权限、`429` 限流、`500` 服务内部错误、`502` 网关收到无效响应、`504` 网关超时。

缓存分强缓存和协商缓存。`Cache-Control: max-age` 决定浏览器在一段时间内直接用本地副本；`ETag` 和 `Last-Modified` 则让浏览器带着标识去问服务端「有没有变」，没变就返回 `304`，省掉正文传输。

## HTTPS 在中间加了什么

HTTPS 不是「把 HTTP 加密一下」这么简单，它是在 HTTP 和 TCP 之间加了一层 TLS。

TLS 握手时，客户端和服务端协商算法、校验证书、交换密钥，最后用对称加密传输数据。非对称加密只用来安全地协商密钥，因为它的开销太大。

证书解决的是「对面是谁」的问题。没有证书，密钥交换本身就可能被中间人截获，加密也就失去了意义。

## 与后端最相关的几个点

第一是超时。连接超时、读超时、写超时要分别设置，任何一项缺失都可能让线程一直挂着。

第二是重试。只对幂等请求重试，并且要有次数上限和退避策略，否则一次故障会被放大成雪崩。

第三是连接池。频繁创建连接的成本很高，池化之后要关注最大连接数、空闲回收和健康检查。

第四是幂等。网络层不保证「只送达一次」，业务层就必须自己设计去重，比如唯一键、令牌或者状态机。

## 用 curl 看一眼真实请求

```bash
curl -v https://example.com/api/health

# 只看响应头
curl -I https://example.com

# 指定方法和请求体
curl -X POST https://example.com/api/orders \
  -H "Content-Type: application/json" \
  -d '{"skuId": 42, "count": 1}'
```

`-v` 会把 DNS 解析、TCP 连接、TLS 握手、请求头和响应头全部打印出来。刚开始学网络时，我经常用它验证自己的理解：到底复用了连接没有，缓存头返回了什么，重定向发生了几次。

## 学完之后

现在再看到「接口很慢」，我会先分清楚是网络层的问题还是应用层的问题：连接建立慢、TLS 握手慢、服务端处理慢，对应的排查方式完全不同。

把两层分开看，是这段学习里最实用的一件事。
