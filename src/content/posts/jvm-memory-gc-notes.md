很长一段时间，我对 JVM 的理解停留在「堆、栈、方法区」三个词。面试能答上来，但线上真的出现频繁 Full GC 时，我并不知道该先看什么。

后来我把 JVM 当成一个正在运行的系统去观察，背过的名词才慢慢变成了一条可以讲清楚的链路。

## 为什么 JVM 值得单独学

最早我觉得 JVM 是面试专用知识：平时写业务代码，好像一辈子都不会碰。

真正开始关注它，是因为一次接口变慢。日志里没有报错，数据库也正常，最后发现问题出在 GC 上：对象创建得太快，年轻代频繁回收，停顿叠加起来就变成了用户感知到的卡顿。

从那以后我才接受一件事：只要程序跑在 JVM 上，内存和回收就和你有关，只是早晚而已。

## 运行时区域：谁跟着线程走

JVM 的内存区域可以先用一个问题来分：这块内存是不是随着线程一起消失。

程序计数器、虚拟机栈、本地方法栈是线程私有的，线程结束它们就结束。堆和方法区（JDK 8 之后叫元空间）是线程共享的，生命周期跟着进程走。

栈里最重要的是栈帧。一次方法调用对应一个栈帧，里面放局部变量表、操作数栈、动态链接和返回地址。方法一层层调用，栈帧就一层层压进去；方法返回，栈帧弹出。递归太深会栈溢出，原因就在这里。

堆里放的是对象。绝大多数对象都在这里出生和消失，所以垃圾回收主要发生在堆上。

记忆时可以抓一个判断标准：私有的跟着线程走，共享的跟着进程走。比单纯背区域名字可靠得多。

## 对象的一生

一个对象被 `new` 出来之后，通常先在 Eden 区分配。Eden 满了触发一次 Young GC，还活着的对象被复制到 Survivor 区，年龄加一。

年龄到阈值（默认 15）之后晋升老年代。大对象可能直接进入老年代，避免在 Survivor 之间反复复制。

这里有个我一开始忽略的点：大部分对象其实活不过第一次回收。分代收集的效率，正是建立在「朝生夕死」这个统计事实之上，而不是某种精巧的算法。

## 怎么判断对象「没用了」

引用计数看起来最直观，但解决不了循环引用：两个对象互相持有，计数永远不为零，却已经没有任何外部引用。

JVM 用的是可达性分析。从 GC Roots 出发，能走到的对象就是活的，走不到就可以回收。

GC Roots 包括虚拟机栈中引用的对象、静态属性引用的对象、常量引用的对象、本地方法栈中引用的对象等。理解这一点之后，很多「内存泄漏」的原因就清楚了：对象本来该结束，却被一个静态集合或未注销的监听器一直牵着。

## 垃圾回收的几种思路

基础算法只有三种：

- 标记-清除：标出垃圾再清掉，简单，但会产生碎片。
- 复制：把存活对象复制到另一块空间，没有碎片，代价是浪费一半空间。
- 标记-整理：标记后把存活对象往一端挪，兼顾空间和碎片，但移动成本高。

年轻代适合复制算法，因为存活对象少；老年代适合标记-整理，因为存活率高。所谓「分代收集」，不过是根据对象存活特征选择了更合适的工具。

## 从 CMS 到 G1

CMS 以低停顿为目标，把回收拆成几个阶段，大部分阶段可以和用户线程并发。它的毛病是碎片和并发失败。

G1 把堆划分成大小相等的 Region，不再要求物理上连续的新生代和老年代。它可以根据停顿目标选择回收哪些 Region，优先回收垃圾最多的那些，所以叫 Garbage First。

JDK 9 之后 G1 成为默认收集器，并不是因为它「更高级」，而是它在吞吐和停顿之间给了更可控的折中。选择收集器时，先问清楚业务要的是吞吐量还是延迟，比背收集器列表有用。

## 看一次真实的 GC

知道原理之后，还需要能看见它。

```bash
# 每秒输出一次 GC 统计
jstat -gcutil <pid> 1000

# 查看堆与元空间使用
jmap -heap <pid>

# 打印 GC 日志（JDK 9+）
java -Xlog:gc*:file=gc.log:time,uptime,level,tags -jar app.jar
```

GC 日志里我会先看三件事：Young GC 的频率、每次停顿的时长、Full GC 有没有出现。频率高说明分配快或年轻代太小；停顿长要看老年代和收集器；出现 Full GC 则要先找是谁把对象堆进了老年代。

这些数字比「JVM 调优」四个字具体得多。

## 调优到底在调什么

调优不是把所有参数都设一遍。它更像是在三个目标之间做选择：吞吐量、停顿时间、内存占用。

常见的参数也就那几个：`-Xms`、`-Xmx`、`-Xmn`、`-XX:MetaspaceSize`。先把堆固定住，避免运行中反复扩缩容；再根据监控决定年轻代大小；最后才考虑收集器和停顿目标。

顺序反了，参数就会越调越乱。先测量，再调整，这个原则和做业务优化没有区别。

## 学完之后

JVM 没有让我立刻写出更快的代码，但它改变了排查问题的顺序：先看现象，再看内存，再看回收，最后才怀疑业务逻辑。

这种从名词到链路的转变，是这段学习里最有价值的部分。
