前面两个项目都有教程，遇到问题可以对照。MukoBazaar 不一样，它是我自己起的名字，也是我第一次在没有标准答案的情况下，把一个集市类应用从表结构写到消息链路。

## 目标与模块

目标很简单：做一个二手与新品混合的交易集市。用户可以发布商品、浏览搜索、加入购物车、下单，卖家处理订单。

拆下来是五个模块：用户、商品、购物车、订单、搜索。没有做支付和物流，这两块复杂度高，而且对我想练习的东西帮助不大。

技术栈是 Spring Boot、MySQL、Redis、RabbitMQ 和 Elasticsearch。

## 表设计：最花时间的部分

写代码之前，我在表结构上停了很久。

商品表和库存表要不要拆开？拆开的好处是库存可以独立更新、独立处理并发；不拆的好处是查询简单，少一次关联。我最后选择拆开，因为下单扣减库存的频率远高于修改商品信息，两者放在一起会让更新互相影响。

订单表也纠结过。订单主体和明细分开是常规做法，但明细里要不要冗余商品名称和价格？从范式上讲不该冗余，可商品信息会变，订单必须保留成交时的快照。

```sql
CREATE TABLE `order_item` (
  `id`           BIGINT        NOT NULL AUTO_INCREMENT,
  `order_id`     BIGINT        NOT NULL,
  `product_id`   BIGINT        NOT NULL,
  `product_name` VARCHAR(128)  NOT NULL COMMENT '成交时的商品名称快照',
  `price`        DECIMAL(10,2) NOT NULL COMMENT '成交单价',
  `quantity`     INT           NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_order_id` (`order_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

商品改名或调价后，历史订单仍然准确。这部分没有教程给答案，每个字段都要自己解释：为什么存这个，为什么冗余那个。

## 订单与库存的一致性

下单的核心问题是：不能超卖，也不能把订单写成功而库存没扣。

我的做法是同步校验加异步处理。用户提交订单时，先在数据库事务里做一次库存校验和预扣，订单状态置为待支付；支付成功后，发送一条消息，由消费者完成真正的库存扣减和订单状态推进。

为什么不用纯异步？因为用户需要立刻知道有没有抢到。为什么不在同步里做完全部？因为下单高峰时，长事务会拖慢响应，也容易锁住热点行。

这套方案不完美。预扣和实扣之间如果消息丢失，库存会一直挂着。所以我又加了一个定时任务，扫描超时未支付的订单，回滚预扣。补偿逻辑比主流程更难写，也更容易被忽略。

## RabbitMQ：可靠投递与幂等

消息链路我做了两件事：保证消息不丢，保证重复消费不出错。

不丢靠三点：生产者开启确认机制，投递失败时回调；队列和消息都持久化；消费者手动确认，处理成功后再 ack。

幂等靠业务唯一键。每条订单消息带一个业务单号，消费者处理前先查这个单号是否已经处理过，处理记录和业务写入放在同一个事务里。这样即使消息重复投递，也只会生效一次。

我踩过一个坑：最初用消息 ID 做去重，但消息重发时 ID 会变，去重失效。换成业务单号之后才稳定下来。

## 搜索：Elasticsearch 与增量同步

商品搜索用 Elasticsearch。商品名称、描述、分类、价格区间这些字段，用 MySQL 的 like 查询既慢又不准，全文检索和分词是更合适的选择。

难点不在查询，而在同步。MySQL 是数据的源头，ES 只是索引。我采用了「数据库写入成功后发送消息，由消费者更新索引」的方式，而不是双写。

这样做的好处是解耦，坏处是存在延迟，也可能因为消费失败导致索引落后。为此我加了一个补偿接口，可以按商品 ID 手动重建索引，另外有一个定时任务对比两边的更新时间。

## Redis 的使用边界

这个项目里 Redis 用得比较克制，只缓存了商品详情和首页列表，并且明确设置了过期时间。

缓存更新采用「先更新数据库，再删除缓存」。商品详情读多写少，这个策略足够。购物车和库存没有放进 Redis，因为前者需要持久化，后者的一致性要求高，我不想在项目初期引入太多需要解释的复杂度。

## 踩过的坑

第一个是状态机遗漏。订单有待支付、已支付、已发货、已完成、已取消几个状态，我最初只写了正常流转，忘了「已支付后取消要退款」和「超时未支付自动取消」这两个分支。测试时才发现订单会卡在中间状态。

第二个是消息重复。前面说过，靠业务单号解决了，但在此之前，重复消费导致库存被多扣了几次。

第三个是索引与数据库不一致。有一次消费者异常退出，商品改了名，ES 里还是旧名字。这个问题不会报错，只会让用户搜到过时的信息，反而更难发现。

## 和课程项目最大的区别

课程项目里，很多决定是教程替我做的：表怎么建、接口怎么分、异常怎么处理，我只需要跟着敲。

MukoBazaar 里没有这个依靠。为什么拆库存表，为什么用消息而不是事务，为什么搜索走 ES 而不是 MySQL，每一个问题都要自己给出理由，并且承担理由不成立时的后果。

这种自己解释的过程很慢，也不舒服，但它让我从会写代码往能做设计挪了一小步。

## 下一步

短期想补三件事：订单状态流转加上乐观锁，避免并发下的重复操作；消息消费增加重试和死信队列；搜索同步做成可观测的，至少能知道落后了多少。

再往后，想试试把服务拆开，用 Spring Cloud 做一次真正的分布式拆分。但在这之前，我更想把现在这套单体的边界理清楚。

项目还在继续。它不完美，但每一行代码我都知道为什么在那里。
