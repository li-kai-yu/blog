索引大概是 MySQL 面试里被问得最多的话题，也是最容易被背成口诀的部分。

「最左前缀」「覆盖索引」「索引下推」这些词，单看结论都能记住，但一旦遇到真实查询，还是很难判断索引到底有没有生效。

这篇文章试着从数据结构出发，把索引的行为推导一遍。

## 为什么是 B+ 树

数据库索引要解决的核心问题是：如何在磁盘上快速找到一条记录。

磁盘随机读取的成本远高于内存，所以索引结构必须尽量矮、尽量宽。B+ 树正好满足这一点：

- 只有叶子节点存数据，非叶子节点只存键值，因此一个节点能放下更多索引项。
- 树的高度通常在 3 到 4 层，查找一条记录只需要少量磁盘 I/O。
- 叶子节点之间用链表连接，范围查询可以顺序扫描。

和 B 树相比，B+ 树的非叶子节点不存数据，扇出更大；和哈希索引相比，B+ 树支持范围查询和排序。这些特性决定了 InnoDB 默认选择它。

## 聚簇索引与二级索引

InnoDB 的表数据本身就存放在主键索引的叶子节点上，这叫作**聚簇索引**。也就是说，一张表只能有一个聚簇索引。

二级索引的叶子节点则存放主键值，而不是完整的行数据。因此，通过二级索引查询时，通常需要两步：

1. 在二级索引中找到主键值。
2. 拿主键值回到聚簇索引中取整行数据。

第二步被称为**回表**。回表不是错误，但它是额外的一次查找。如果查询只需要索引里已有的列，就可以避免回表，这就是覆盖索引的价值。

## 最左前缀不是玄学

联合索引 `(a, b, c)` 的排序规则，是先按 `a` 排，再按 `b` 排，最后按 `c` 排。

因此它可以支持：

- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c = ?`
- `WHERE a = ? AND b > ?`（`a` 等值，`b` 范围）

但不能高效支持：

- `WHERE b = ?`
- `WHERE a = ? AND c = ?`（`c` 无法利用索引排序）

「最左」不是指 SQL 里必须把 `a` 写在最前面，而是指查询条件必须从索引的最左列开始，且不能跳过中间列。

一个常见的误区是：`WHERE a = ? AND c = ?` 里 `c` 完全用不上索引。实际上优化器可以用 `a` 定位，再用「索引下推」在索引层过滤 `c`，减少回表次数。这已经是 MySQL 5.6 之后的优化，但和「利用 `c` 做范围定位」是两回事。

## 覆盖索引与索引下推

**覆盖索引**指的是查询需要的列全部包含在索引中，不需要回表。

```sql
CREATE INDEX idx_user_status_name ON users (status, name);

-- 需要回表：查询 select *，索引里没有全部列
SELECT * FROM users WHERE status = 1;

-- 覆盖索引：只取索引中已有的列
SELECT name FROM users WHERE status = 1;
```

`EXPLAIN` 的 `Extra` 列出现 `Using index`，通常就表示使用了覆盖索引。

**索引下推**（Index Condition Pushdown）则是在存储引擎层提前过滤不满足条件的列，减少回表次数。`Extra` 中会显示 `Using index condition`。

这两个优化都说明一件事：索引不是只有「用」和「不用」两种状态，中间还有很多层次。

## 用 EXPLAIN 验证，而不是猜

判断索引是否生效，最可靠的方式还是看执行计划。

```sql
EXPLAIN SELECT id, name
FROM users
WHERE status = 1 AND name LIKE 'A%'
ORDER BY created_at DESC
LIMIT 20;
```

需要关注几个字段：

- `type`：访问类型，`ref`、`range` 通常比 `index`、`ALL` 好。
- `key`：实际使用的索引。
- `rows`：预估扫描行数。
- `Extra`：是否出现 `Using where`、`Using filesort`、`Using temporary`。

看到 `Using filesort` 不一定意味着性能差，但如果数据量大、排序又无法利用索引，就值得重新考虑索引顺序。

## 索引也会带来成本

索引不是越多越好。

- 每个索引都占用磁盘空间。
- 写入时需要维护所有相关索引，插入和更新会变慢。
- 优化器面对过多索引时，也可能选错执行计划。

设计索引时，我更倾向于从真实查询出发：先收集高频 SQL，再看它们的过滤条件、排序字段和返回列，最后决定组合。而不是先给每个字段都加一个索引。

## 一个简单的判断流程

遇到慢查询时，我会按这个顺序检查：

1. 用 `EXPLAIN` 确认是否走索引，以及走的是哪个索引。
2. 检查联合索引的列顺序是否匹配查询条件。
3. 看能否通过覆盖索引消除回表。
4. 检查排序和分组是否能复用索引。
5. 最后再考虑改写 SQL 或调整索引结构。

索引设计的本质，是让数据按照查询需要的方式排列。理解这一点，比记住任何一条口诀都更有用。
