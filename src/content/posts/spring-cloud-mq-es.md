单体应用写得顺手之后，人会不自觉地认为「拆开」只是多建几个工程。

真正开始学微服务，我才发现拆开之后，原来那些被框架悄悄兜住的问题，会一个接一个浮上来：服务怎么找到彼此，调用失败怎么办，数据一致怎么保证，消息丢了怎么查。

这篇文章记录我在这个阶段的理解，尽量不写成组件手册。

## 为什么开始学微服务

我的出发点很朴素：项目变大了，一个工程里塞了太多模块，改一处要重新部署全部，心里没底。

微服务提供了一种拆分思路：按业务边界切开，每个服务独立部署、独立演进。它带来的不只是技术变化，更是组织方式的变化——谁负责哪块，边界在哪里，都要提前想清楚。

## 四个组件，四种职责

刚接触 Spring Cloud 时，组件很多，名字也容易混。后来我按「它解决什么问题」来记，清楚了很多。

### Nacos：注册与配置

Nacos 同时承担两件事：服务注册发现和配置管理。

服务启动时把自己注册进去，调用方通过服务名找到实例列表，不必写死 IP。配置中心则把散落在各个工程里的配置收拢起来，改完可以动态刷新。

### OpenFeign：把远程调用写成本地方法

OpenFeign 用接口加注解的方式声明远程调用，调用方看起来像在调本地方法。

方便的背后是风险：网络调用会超时、会失败、会重试。写 Feign 接口时，如果不考虑超时和降级，出问题时往往很难定位。

### Gateway：统一入口

网关是所有外部请求的第一站。路由转发、鉴权、限流、日志，都可以在这里统一处理，而不是让每个服务各写一遍。

它像一个门卫，也像一个收口。对外只暴露一个地址，内部服务怎么变，外部不必知道。

### Sentinel：限流与熔断

Sentinel 关注的是稳定性。流量超过阈值时限流，依赖服务不稳定时熔断，避免故障沿着调用链扩散。

我一开始把它当成「加个注解就行」的工具，后来才明白，规则怎么定、阈值怎么设，比接入本身更难。

## 拆分之后的分布式事务

单体应用里，一个本地事务就能保证一致性。拆成多个服务后，一次业务操作可能跨越好几个数据库，本地事务管不到了。

这就是分布式事务问题。Seata 提供了几种模式，其中 AT 模式对业务侵入较小，适合大多数常规场景。

但它不是万能药。强一致往往意味着性能和复杂度上的代价，很多业务其实可以接受最终一致。我的判断是：先问业务能不能容忍短暂不一致，再决定要不要引入分布式事务框架。为了「看起来严谨」而上 Seata，反而容易把系统做重。

## RabbitMQ：消息的另一面

消息队列最直观的价值是解耦和削峰。下单后异步通知、积分、日志，这些不必卡在主流程里。

但引入消息之后，问题也随之而来。

### 可靠投递

消息可能在生产端丢失，也可能在消费端丢失。常见的做法是：生产端开启确认机制，消费端手动确认，配合持久化，确保消息不会因为服务重启而消失。

### 消费幂等

消息可能重复投递，这是分布式系统的常态。消费逻辑必须做到重复执行结果一致，比如用唯一业务单号做去重，或者用状态机限制重复流转。

### 消息堆积

堆积通常不是 MQ 的问题，而是消费能力跟不上。先看是消费逻辑慢，还是消费者太少，再决定优化代码还是扩容。盲目加机器有时只是把问题往后推。

## Elasticsearch：搜索是另一套逻辑

用 MySQL 做模糊查询，数据量一大就会吃力。Elasticsearch 的价值在于倒排索引：它记录的是「词出现在哪些文档里」，而不是逐行扫描。

这个结构决定了它擅长全文检索和相关性排序，但不适合当主数据库。它不擅长事务，也不适合频繁更新。

### DSL 查询

ES 用 JSON 描述查询，条件、过滤、排序、聚合都可以组合。刚开始写 DSL 会觉得啰嗦，熟悉之后会发现它的表达力很强，尤其是组合条件和聚合统计。

### 与 MySQL 的同步

这是最容易出问题的地方。常见做法有同步双写、基于 binlog 的异步同步、定时任务补偿。

同步双写简单，但可能不一致；binlog 方案更可靠，但多了一套链路要维护。无论选哪种，都要接受一个事实：搜索数据允许有延迟，关键是延迟是否在业务可接受范围内。

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
      config:
        server-addr: 127.0.0.1:8848
        file-extension: yaml
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1
```

这段配置把注册、配置和网关放在一起，能看出微服务的入口是怎么组织的。

## 三者如何配合

一个典型的下单链路可以这样理解：

请求先经过 Gateway，路由到订单服务；订单服务通过 OpenFeign 调用库存服务，Sentinel 守在调用链上；下单成功后，往 RabbitMQ 投递一条消息，由其他服务异步消费；商品数据通过同步机制进入 Elasticsearch，供搜索接口查询。

每个组件只负责一段，串起来才是一个系统。任何一段出问题，都可能表现为整体变慢。

## 不要为了微服务而微服务

学完这些，我反而更谨慎了。

微服务解决的是规模和组织问题，不是代码质量问题。一个小项目强行拆成七八个服务，只会让部署、调试、排错都变难。消息队列和搜索引擎也一样，它们是工具，不是标配。

我现在判断要不要引入一项技术，会先问三个问题：当前真的痛吗，不引入能不能解决，引入之后谁来维护。

回答不清楚，说明还不到时候。
