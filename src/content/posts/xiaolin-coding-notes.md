学校的课程像一张地图：知道有网络、有操作系统、有数据库，也知道它们各自重要。

但地图不等于路。真正走到细节里，我才发现自己说不清一次请求是怎么发出去的，也讲不出索引为什么能加速查询。

那段时间我开始系统补课，主要用的是小林coding 的图解系列。这篇记录我补课的顺序和一些想明白的地方。

## 为什么需要补课

我的第一门专业课是计算机网络。教材很厚，概念很多，考试也能过。

可当面试官问我「浏览器输入网址之后发生了什么」，我只能给出一个模糊的流程：DNS、TCP、HTTP、渲染。再往下问三次握手为什么不是两次，我就答不上来了。

问题不在于没学过，而在于学得太散。概念之间没有连成链路，考试一结束就散掉了。

## 图解网络：终于看懂一次请求

小林coding 的图解网络，是我补课的第一站。

它把 TCP 的状态机画了出来：SYN、SYN-ACK、ACK 分别对应哪一方、什么状态。配合三次握手的图，我才真正理解为什么两次不够：服务端需要确认客户端也具备接收能力。

第二次让我停下来的是 `TIME_WAIT`。以前只知道「要等两个 MSL」，看了图解之后才明白，它既是为了让最后的 ACK 有机会到达，也是为了避免旧连接的报文干扰新连接。

把这些细节补上之后，再回看 HTTP/1.1 的长连接和 HTTP/2 的多路复用，整条链路终于连贯了：应用层的语义，最终都要落到传输层的连接上。

## 图解操作系统：内存与进程不再抽象

操作系统是我最没感觉的一门课。虚拟内存、页表、进程调度，全是抽象名词。

图解操作系统改变了我看这些概念的方式。它把虚拟地址到物理地址的转换画成一条路径：页表、多级索引、缺页中断。那一瞬间我才理解，为什么内存看起来是连续的，实际却可以打散在物理内存里。

进程与线程也一样。以前只知道「线程共享进程的内存」，补课之后才把它和上下文切换、信号量、IO 多路复用连起来。后来写 Java 并发时，很多设计终于有了出处。

## 图解 MySQL 与 Redis：把索引和缓存落到数据结构

数据库部分，我最大的收获是把「结论」换成了「推导」。

索引为什么用 B+ 树？因为要减少磁盘 IO，B+ 树矮胖、叶子节点串成链表，适合范围查询。这句话以前是背的，看完图解之后，我能自己把树的高度、页的大小和一次查询的 IO 次数算一遍。

Redis 也是类似。五种基本类型的底层编码、跳表、渐进式 rehash，这些细节看起来偏面试，但真正帮助我理解的是：为什么单线程还能这么快，什么情况下会慢。

## 图解不是终点

图解看得再明白，不动手还是会忘。

所以我给自己配了验证手段：网络部分用 `curl -v` 看握手和响应头，数据库部分用 `EXPLAIN` 看执行计划，JVM 部分用 `jstat` 看 GC。图解负责建立模型，工具负责检查模型有没有偏差。

两者对不上时，说明我理解错了，这反而是最有价值的时候。

## 最后

小林coding 的图解系列帮我补上了学校课程没讲透的细节，也让我第一次感觉到：网络、操作系统、数据库不是三门孤立的课，而是同一个系统在不同层面的样子。

补课的意义，不是多背几个结论，而是以后看问题时，能顺着链路往下想一层。
